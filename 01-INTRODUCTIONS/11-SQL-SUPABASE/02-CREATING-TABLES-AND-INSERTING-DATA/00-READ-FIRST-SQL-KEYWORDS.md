## 1. INSERT INTO and VALUES

```sql
INSERT INTO teachers (name)
VALUES ('Ali');
```

This means: **insert a new row into the teachers table, putting the text Ali in its name column**.

| Piece | Meaning | Purpose |
| --- | --- | --- |
| INSERT | Insert (add) data | Names the action |
| INTO | Into this destination | Introduces the target table |
| teachers | The table to receive data | Names the destination |
| (name) | List of target columns | Specifies which column receives the value |
| VALUES | These are the supplied values | Begins the values clause—even for a single row |
| ('Ali') | One row of values | A quoted SQL text string |
| ; | End of the statement | Separates SQL statements |

`INSERT` describes the action. `INTO` connects that action to its destination; it is **not** a second action. In PostgreSQL INSERT syntax, use **VALUES**, not `VALUE`, even for one row.

### Two columns

```sql
INSERT INTO teachers (id, name)
VALUES (7, 'Sara');
```

The first value 7 maps to `id`; the second value 'Sara' maps to `name`. SQL string literals use single quotes. The column names and values must align in number, order, and compatible type.

### Multiple rows

```sql
INSERT INTO teachers (id, name)
VALUES (8, 'Mina'),
       (9, 'Carlos');
```

Each parenthesized group represents a new row. Commas separate rows and column names.

## 2. CREATE TABLE

```sql
CREATE TABLE teachers (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL
);
```

- `CREATE` creates a database object.
- `TABLE` specifies that object is a table.
- `teachers` names the table.
- `id` and `name` name its columns.
- `INTEGER` is a whole-number type.
- `TEXT` stores text strings.
- `PRIMARY KEY` disallows duplicate or NULL identifiers.
- `NOT NULL` rejects SQL NULL, **not** an empty string.
- Parentheses surround definitions; commas separate columns; semicolon terminates the statement.

A CREATE TABLE command defines a structure; it does not add student or teacher records.

## 3. PRIMARY KEY Is Not Automatic Numbering

```sql
id INTEGER PRIMARY KEY
```

This enforces a unique non-NULL key, but **does not generate IDs** in PostgreSQL. If there is no default, omitting the ID during INSERT fails.

## 4. What Does IDENTITY Mean?

```sql
id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

- `GENERATED`: The database generates a value.
- `ALWAYS`: Explicit values are normally forbidden unless a special override is supplied.
- `AS IDENTITY`: Declare an automatically generated identity column backed by a sequence.
- `PRIMARY KEY`: A separate constraint still verifies uniqueness/non-NULL.

Without an explicit ID, PostgreSQL uses the identity sequence:

```sql
INSERT INTO teachers (name) VALUES ('Peyman');
```

## 5. ALWAYS versus BY DEFAULT

```sql
id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
```

`BY DEFAULT` means auto-generate an ID when the INSERT omits it, but accept a manually supplied one when present.

| Declaration | Omit ID | Supply ID manually |
| --- | --- | --- |
| INTEGER PRIMARY KEY | Error without a default | Allowed if unique |
| GENERATED ALWAYS AS IDENTITY PRIMARY KEY | Auto-generate | Rejected normally |
| GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY | Auto-generate | Allowed if unique |

## 6. OVERRIDING SYSTEM VALUE, Explained Word by Word

```sql
INSERT INTO teachers (id, name)
OVERRIDING SYSTEM VALUE
VALUES (50, 'Peyman');
```

Assume `id` was defined as `GENERATED ALWAYS AS IDENTITY`.

| Phrase | Meaning |
| --- | --- |
| INSERT INTO teachers | Insert a row into teachers |
| (id, name) | Assign these two columns |
| OVERRIDING | Intentionally override a normal rule |
| SYSTEM VALUE | Allow the user's explicitly provided identity value instead of requiring system generation |
| VALUES (50, 'Peyman') | Insert ID 50 and name Peyman |

**It does not turn off PRIMARY KEY**: if 50 already exists, the INSERT still fails. It also does not automatically move the associated sequence counter to 51. This special syntax is useful in carefully controlled migrations and normally unnecessary for everyday app inserts.

### Different phrase: OVERRIDING USER VALUE

`OVERRIDING USER VALUE` tells PostgreSQL to ignore explicitly provided identity values and generate fresh ones. Do not confuse **SYSTEM** (accept user's value for an ALWAYS identity) with **USER** (use generated identity values).

## 7. Sequence Behavior

A PostgreSQL sequence provides a stream of numeric values for identity columns.

- An ID is an identifier, not a row count.
- Deleted values are normally **not reused** automatically.
- Explicitly supplying ID 100 does not necessarily move the sequence to 101.
- A failed INSERT can consume a sequence value; sequences are not normally rolled back.
- Gaps in IDs are normal.

```sql
SELECT COUNT(*) FROM teachers;
```

This counts actual rows; the maximum ID does not.

## 8. NULL versus Blank Text

`NULL` means an absent/unknown SQL value, while `''` is an actual string containing zero characters. A `TEXT NOT NULL` column rejects `NULL` but accepts `''`. A CHECK constraint can be added to prohibit blank/whitespace-only names.

5. What does `GENERATED BY DEFAULT AS IDENTITY` allow that ALWAYS normally does not?

8. Why might a generated ID sequence contain gaps?

### Answers for Self-Review

1. INSERT identifies the operation; INTO introduces the destination.
2. `teachers`.
3. `VALUES ('Ali')`.
4. No; use an identity/default mechanism.
5. Explicit user-supplied IDs without an override clause.
6. It accepts a specified historic ID into an ALWAYS identity column.
7. No; PRIMARY KEY uniqueness still applies.
8. Deletes and failed inserts may leave unused IDs, and sequences do not promise continuous numbering.
